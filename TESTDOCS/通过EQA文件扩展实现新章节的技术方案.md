# 通过 EQA 文件扩展实现新章节的技术方案

## 概述

本文档分析在 **Love Escalator**（PC-98 美少女游戏）中新增完全原创的游戏章节的技术可行性。核心思路是：利用 EQA 脚本引擎的**顺序读取特性**，在不修改游戏引擎二进制的前提下，通过向现有 `.eqa` 文件中追加文本条目来嵌入新剧情。

---

## 一、EQA 文件格式总览

每个 `.eqa` 文件是一个自包含的游戏脚本，由以下部分组成：

```
[文件头] ─→ [跳转表/场景标识]
    ↓
[控制指令] ─→ 资源加载（BGM、背景、立绘）
    ↓
[文本条目 0] ─→ 00 [ROM 编码字节] 01 23 00 15 XX XX
    ↓
[控制指令] ─→ 人物动作、选项、场景过渡
    ↓
[文本条目 1] ─→ 00 [ROM 编码字节] 01 23 00 15 XX XX
    ↓
...
    ↓
[文本条目 N] ─→ 00 [ROM 编码字节] 01 23 00 15 XX XX
    ↓
[场景结束代码] ─→ 67 66 0B ... 3D 85 ... 18 3D 82 31 01 4C 4F 56 45 00 ... 2C 00 16
                    ↑ 场景结束标记     ↑ 跳转回主循环（LOVE）
```

### 文本条目格式

| 偏移 | 字节 | 含义 |
|------|------|------|
| +0 | `00` | 条目前缀 |
| +1 ~ +M | ROM 编码序列 | 对话/叙述文本 |
| +M+1 ~ +M+2 | `01 23` | 说话人结束标记（」） |
| +M+3 ~ +M+6 | `00 15 XX XX` | 条目尾部（XX XX 可能是长度或校验和） |

### ROM 编码规则

- 双字节字符码（高字节 +0x20 即 JIS 区位码）
- 单字节操作码：
  - `81` = 换行
  - `22` = 说话人开始（「）
  - `23` = 说话人结束（」）
  - `90` / `92` = 主角名字替换
  - `01 XX` = 资源名前缀（后接 ASCII 字符）

## 二、引擎读取机制

### 顺序执行

游戏引擎对 `.eqa` 文件的处理是**线性顺序**的：

1. 从 LOVE.EAR 存档中读取文件全部数据（通过索引表得到偏移 + 大小）
2. 从文件头开始逐字节解释
3. 遇到 `00` 字节且后续为有效 ROM 编码时，视为文本条目开始
4. 读取到 `01 23 00 15 XX XX` 时，文本条目结束
5. 遇到控制指令（如 `1E 0B`, `3D 85` 等），执行对应操作
6. 遇到 `67 66 XX` 系列指令时，执行场景跳转或返回
7. 最终遇到 RESIO → LOVE（`18 3D 82 31 01 4C 4F 56 45 00`）时，当前场景结束，返回主循环

### 文件尾部的关键结构

所有 `.eqa` 文件的末尾都有高度一致的页脚：

```
67 68 18 3D 82 31 01 4C 4F 56 45 00 1E 0C 00 4E 0A 01 3C 12 20 E1 57 2A 32 01 42 4F 4F 54 4D 45 4E 55 00 2C 00 16
```

解码：
- `31 01 4C 4F 56 45 00` = 场景标识 `LOVE`（主循环）
- `32 01 42 4F 4F 54 4D 45 4E 55 00` = 场景标识 `BOOTMENU`（引导菜单）
- `2C 00 16` = 文件结束符

**这意味着：引擎在读取文件时，会一直运行到遇到文件结束符为止。在 RESIO 段之前插入的任何新数据都会被正常处理。**

## 三、容量限制分析

### 当前约束

| 约束来源 | 实际是否限制 | 说明 |
|---------|------------|------|
| `pack.js` 的 `LOVE_EAR_JP_LEN` 检查 | **硬限制** | 第 54-56 行 throw，防止总大小与原始日文 ISO 不符 |
| HDI 磁盘镜像（FAT12） | 软限制 | 31,177,216 字节镜像，当前 LOVE.EAR ~25.5MB，空余 ~5.6MB |
| LOVE.EAR 存档索引 | 无限制 | `pack.js` 自动重新计算各文件偏移和大小 |
| FAT12 文件系统 | 无限制 | `replaceHdiFile.js` 的 `replaceFile()` 通过释放旧簇+分配新簇支持变长文件 |

### 解除限制

**只需删除 `pack.js` 的第 54-56 行：**

```javascript
// 删除以下三行：
if (resultBuffer.length !== LOVE_EAR_JP_LEN) {
    throw `打包的 ${destFile} 的文件长度与原版日文 LOVE.EAR 长度不一致，可能有错误`
}
```

解除后，LOVE.EAR 可以容纳任意大小的文件（受 HDI 空余空间限制）。

### 空间容量估算

| 目标 | 约需空间 | 是否可行 |
|------|---------|---------|
| 扩写现有 325 条条目（填满 00 填充） | ~8 KB | ✅ 天生可行 |
| 新增约 2,500 条文本条目（~10 万字章节） | ~205 KB | ✅ HDI 剩余 5.6MB |
| 极端情况（HDI 全部用满） | ~5.6 MB | ✅ 理论极限约 70 万字 |
| 添加新图像资源（.ecg） | 视数量而定 | ✅ 需同时处理文件头跳转表 |

## 四、添加新文本条目的工作流

### 方案 A：通过 table.json 扩写（≤8KB）

适用范围：仅用完现有 00 填充空间，不改文件大小。

```
1. 修改 table.json → 扩展 dth.eqa 各条目的 cn 字段
2. npm run hex     → 自动转换 ROM 编码、平衡组级长度
3. npm run pk      → 重新打包（不改 pack.js）
4. npm run hdi     → 注入 HDI
```

**优点**：完整利用现有管线，自动化程度高。
**缺点**：不能超过原日文文本总字节长度。

### 方案 B：直接追加二进制条目（容量无上限）

适用范围：创建全新章节，远超原文件容量。

```
1. npm run hex       → 先处理已有 table.json 条目
                       生成 ear_cn/dth.eqa
2. 自定义追加脚本     → 在 ear_cn/dth.eqa 的最后一条之后、
                       RESIO 页脚之前插入新条目
                       新条目格式：00 [ROMCODE] 01 23 00 15 XX XX
3. npm run pk        → 重新打包（已改 pack.js，不加大小检查）
4. npm run hdi       → 注入 HDI
5. 测试

※ 每次 npm run hex 后都必须重新运行自定义脚本
```

**优点**：无上限，可添加任意数量的新内容。
**缺点**：需要维护专用追加脚本，脱离 table.json 管线。

## 五、技术风险与对策

| 风险 | 概率 | 对策 |
|------|------|------|
| 引擎不识别过长文件 | 低 | 引擎通过 LOVE.EAR 索引表读取文件大小，支持任意长度 |
| 文本条目格式错误导致崩溃 | 中 | 追加脚本严格遵循 `00 [ROMCODE] 01 23 00 15 XX XX` 格式 |
| 场景结束指令损坏 | 低 | 不修改末尾 RESIO 页脚 |
| 文件头引索表未更新 | 低 | 新条目不经过文件头跳转表，由引擎顺序读取 |
| 游戏存档兼容性 | 中 | 新增场景位于已有场景内部，不影响存档变量 |
| `npm run hex` 覆盖自定义内容 | 确定 | 需在 CI/构建流程中确保追加脚本在 hex 之后自动运行 |

## 六、推荐实施步骤

### 第 1 阶段：验证管线（2-3 天）

1. 修改 `pack.js` 移除大小检查
2. 选择 `pr.eqa`（20 条）作为试目标
3. 向 `pr.eqa` 末尾追加 5-10 条测试文本
4. 打包、注入、测试

**通过标准**：模拟器中看到新文本显示。

### 第 2 阶段：扩写雏子约会场景（3-5 天）

1. 将 `dth.eqa` 的 325 条 CN 文本全部重写
2. 利用 7,712 字节填充嵌入新章节前置内容
3. 打包、注入、测试

### 第 3 阶段：追加全新章节（视文本创作进度）

1. 开发追加脚本（Node.js，使用现有 `jp2RomCode()` 模块）
2. 将创作好的 CN 文本批量转换为 ROM 编码条目
3. 注入 `dth.eqa` 末尾，位于 RESIO 页脚前
4. 打包、注入、测试

### 追加脚本核心代码

```javascript
const { jp2RomCode, REV_NAME_DICT } = require('./romCode2JP')
const { 半角转全角, 中文转日区 } = require('./utils')

function createEntry(cnText) {
    // 步骤 1: 中文 → 日区汉字 → ROM 编码
    cnText = 半角转全角(cnText)
    cnText = 中文转日区(cnText)
    const romCode = jp2RomCode(cnText)
    
    // 步骤 2: 组装条目二进制
    const bytes = ['00', ...romCode, '01', '23', '00', '15', '7A', '1E']
    return Buffer.from(bytes.join(''), 'hex')
}
```
